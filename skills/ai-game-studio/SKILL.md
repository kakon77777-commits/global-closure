# AI Game Studio — Three Architects

Build the user's requested game through three accountable disciplines: **programming**, **art**, and **design**. Each architect chooses methods, creates or adapts the necessary production tools, uses them to produce game content or behavior, and verifies their contribution in the integrated game. A tool roadmap alone is not delivery.

## Compose the existing methods

Use **global-first-completion** for whole-scope implementation and bounded validation. Use **mssp-tdd-apr** for shared project state, event-local Lead/Twin allocation, falsifying witnesses, and distinct behavioral, structural, and discriminative claims. Load these named skills once per context when applying them; resolve by name, not installation ID. Read [method integration](references/methods.md) for source locations or a missing dependency.

This is the user's **three-architect extension** of the two-context MSSP profile, not a claim that the original profile uses three contexts. For each consequential cross-discipline issue, choose one Lead and one relevant peer among the three existing architects. The third continues its own work or stays idle. Do not add a permanent fourth manager or a Twin for each architect. Reuse the same necessary checks across methods rather than stacking full workflows.

For an isolated demonstrated defect, LSPR may guide minimal replacement; it is not a mandatory extra phase.

## Bind a role and a common game

At entry, resolve the shared project location, current scope and revision, assigned role, available tools, and actual context/transport capabilities. Read current artifacts before relying on conversational recollection. Continue under established decisions; ask only for a missing choice that materially changes the game or authority.

| Architect | Owns | Typical executable means | Read only for this role |
| --- | --- | --- | --- |
| Programming | Runtime architecture, gameplay implementation, integration, build and diagnostics | Importers, simulation/replay harnesses, generators, profilers, editor extensions | [Programming](references/programming.md) |
| Art | Visual direction, asset families, production parameters and visual acceptance | Parameterized asset tools, previewers, generation orchestration, atlas/animation metadata and engine import tools | [Art](references/art.md) |
| Design | Player experience, mechanics, progression, levels, economy and balance | Rule simulators, level/content generators, tuning editors, constraint checkers and playtest analysis | [Design](references/design.md) |

Roles are responsibilities, not limits on technical capability: art and design architects write their own tools and algorithms. The programming architect coordinates runtime compatibility; it is not the mandatory author of every tool. Record the current integration owner, usually programming, without making it a separate role.

Preserve the selected engine, target platform, artistic direction, and game identity unless evidence and user scope justify a change. Favor Windows/PowerShell for local instructions when the project has not selected another platform.

## Tools must serve the playable result

Choose the smallest project-specific tool or algorithm that removes a real production bottleneck. Reuse engine facilities or existing tools where sufficient; an executable configuration or thin extension can be the right tool. Do not build a general engine or universal editor before the game exists.

Agree only the cross-discipline contracts needed now: identifiers, units, coordinates, input/output schemas, asset dimensions or pivots, animation/event names, and runtime budgets where relevant. Keep one authoritative source for each rule. These examples are not a mandatory checklist.

For each role's active production need, deliver **an executable tool or algorithm, a real output produced with it, and evidence that the game or its declared consumer uses that output**. Record how to rerun it and the important parameters, seeds, source inputs, and limitations. Do not count an unused tool, placeholder manifest, disconnected mockup, or prose-only design as the requested game feature.

Instantiate the whole requested playable scope before polishing a subsystem. Allow cheap local syntax and contract checks during construction; concentrate integration validation after the main path exists. Use executable behavior witnesses without enforcing a full review after every edit. Inspect visual results in context and use playtests for experience claims; a green parser does not establish visual quality or fun.

## Work across real conversations

Read [cross-conversation handoff](references/handoff.md) when opening or resuming a role, changing ownership, or delivering to another context. Use shared durable project artifacts as the common world. Pin the revision and relevant contract/asset hashes; exchange concise deltas, evidence, unresolved questions, and the next action.

Bind role labels to host-observed contexts when available. Use an authorized native context-messaging tool when it exists; otherwise use repository/file handoffs. Files preserve asynchronous continuity but do not wake another conversation. Never claim a packet was read, a peer agreed, or an independent review occurred without a receiver-produced result. One context playing all roles is explicitly a sequential, degraded mode.

Delegate only a bounded implementation or inspection task with input references, output contract, write boundary, completion evidence and relevant authority. Use actual available agents/providers; do not invent access or spawn recursive worker trees. The architect integrates and accepts the result. The user's request to coordinate AI roles does not grant credentials, unlimited paid calls, publication, or unrelated messaging authority.

## Close the game, preserve the next entry point

After the whole requested path is connected, run the relevant build/playthrough and verify the art and design outputs are actually consumed. Batch related repairs, then rerun affected checks and the necessary final integrated witness. Stop when the agreed scope is satisfied.

Report the playable artifact, each role's tool/output contribution, observed validation, and actual blockers. Keep behavior, reconstruction, and validator discrimination claims separate. Preserve unknowns such as unmeasured balance, uninspected visuals, or an unavailable peer. Save the compact current state and any pending handoff so another conversation can resume without the full chat.
